# 01 - Problem Audit v1

## Audit Summary

Este Stage 01 separa problemas reales de deseos, soluciones favoritas y opciones tecnicas. La evidencia principal procede del Stage 00 aprobado y de sus `SRC-*`; no se reabren las decisiones arquitectonicas ya marcadas como tomadas, pero si se audita si responden a dolores operativos reales.

El problema de fondo no es "instalar IA" ni "elegir herramientas". El problema real es que DClick opera una consultoria de subvenciones con vigilancia manual, atencion reactiva, documentacion dispersa, memoria comercial fragil y usuarias principales no tecnicas. El sistema puede resolver parte de estos dolores con automatizacion, procesos y gobierno; no puede resolver de forma honesta los riesgos legales, de consentimiento, adopcion y calidad sin decisiones operativas adicionales.

En esta etapa, "MVP Relevance" se interpreta como relevancia para el alcance base interno de decision de Stage 02. No debe usarse como framing comercial de "fase 1/fase 2" ante DClick. [SRC-001] [SRC-002]

## Wishes, Ideas, and Unsupported Assumptions

- "Usar IA" no es un problema; los problemas son vigilancia, atencion, documentacion, memoria comercial, produccion repetitiva y gobierno.
- Hermes no es un problema ni una opcion exploratoria; es la arquitectura objetivo para el runtime agentic salvo bloqueo grave. Stage 03 debe disenar implementacion, pruebas tecnicas y limites, no reabrir si Hermes entra. [SRC-002] [SRC-005] [SRC-018]
- Kapso + Hermes no es una hipotesis debil; es la via objetivo de WhatsApp salvo bloqueo grave. El problema real es soportar WhatsApp de forma segura, trazable, con opt-in, templates, numero y costes claros. [SRC-002] [SRC-011] [SRC-018]
- n8n como core conversacional/agentic queda descartado. Solo podria aparecer como auxiliar puntual si una integracion ad hoc lo justificara. [SRC-001] [SRC-002] [SRC-005]
- Elegir CRM concreto no es el problema de Stage 01. El problema es la memoria comercial manual y la necesidad de seguimiento estructurado. [SRC-013]
- Elegir pgvector, Postgres FTS, SQLite FTS5, Chroma o LanceDB no es el problema. El problema es recuperar conocimiento con citas y fuente auditable sin convertir el indice en fuente de verdad. [SRC-008]
- Shared Drive vs carpeta compartida gobernada no es el problema. El problema es que Drive sea superficie humana controlada y que el mirror tecnico sea regenerable, no un sync caotico. [SRC-006]
- Envio autonomo masivo de campanas no esta soportado como problema a resolver sin aprobacion humana. La preparacion de campanas si esta soportada; el envio requiere opt-in, bajas y aprobacion. [SRC-002] [SRC-014] [SRC-015]
- Stage 06 o plan de ejecucion detallado no es un problema actual porque `execution_plan_enabled` esta en `false`; si se quiere plan de ejecucion, debe cambiarse de forma explicita mas adelante. [SRC-019]
- Una migracion historica completa de todo OneDrive/correo no esta probada como necesidad de alcance base; la necesidad confirmada es gobernar la documentacion operativa y evitar fuentes de verdad duplicadas. [SRC-001] [SRC-006]

## MVP Candidates

Estas candidaturas no son alcance aprobado; son candidatos para que Stage 02 decida que entra en el alcance base interno y que queda como evolucion funcional futura.

- Radar BDNS/Canarias minimo: fetch/deteccion diaria, deduplicacion, resumen, scoring inicial, landing zone y alerta a Drive/email/WhatsApp interno. [SRC-001] [SRC-007]
- Drive gobernado + mirror tecnico: carpeta o Shared Drive controlado, manifests, sync no caotico, Markdown operativo e indice derivado. [SRC-006] [SRC-008]
- Hermes core operativo: gateway agentic, toolsets, workers deterministas, logs, permisos y pruebas tecnicas de integracion. [SRC-002] [SRC-005] [SRC-018]
- WhatsApp via Kapso + Hermes: numero dedicado, webhooks, allowlists, opt-in/templates y fallback Cloud API directa si Kapso bloquea coste/estabilidad/limites. [SRC-002] [SRC-011] [SRC-018]
- Email/Gmail dedicado: hilos, labels, adjuntos, clasificacion de riesgo, drafts/respuestas y escalado. [SRC-012]
- Atencion autonoma low-risk: acuses, FAQs, peticion de datos, consultas genericas con fuente, derivacion humana y registro CRM. [SRC-010] [SRC-015]
- CRM adapter agnostico: contacto, oportunidad, conversacion, tarea, nota, tag y estado minimo, sin cerrar CRM concreto antes de Stage 02/03. [SRC-013]
- Equipo IA analista inicial: analisis de convocatoria y subconjunto de outputs estandar con logs y validacion humana cuando aplique. [SRC-009]
- Campanas preparadas, no enviadas sin aprobacion: segmentacion, borradores, plantillas, unsubscribe/opt-in y metrica basica. [SRC-014] [SRC-015]
- Capa de seguridad/evals/observabilidad/training: reglas de riesgo, logs, fixtures, golden answers, runbooks y entrenamiento de Vivi/Maria. [SRC-015] [SRC-016] [SRC-017]

## Out-of-Scope or Weakly Supported Problems

- "Crear una IA general para todo DClick" es demasiado amplio y no esta delimitado como problema operativo resoluble.
- "Automatizar todo sin revision humana" contradice los riesgos de RGPD, calidad, campanas y casos de alto riesgo. [SRC-010] [SRC-014] [SRC-015]
- "Enviar campanas masivas autonomamente" queda fuera salvo aprobacion humana, opt-in y bajas. [SRC-002] [SRC-014] [SRC-015]
- "Usar Baileys/WhatsApp Web en produccion" queda descartado como via productiva. [SRC-011] [SRC-018]
- "Convertir n8n en core" queda descartado; no resuelve mejor el dolor agentic central y contradice la decision actual. [SRC-001] [SRC-002] [SRC-005]
- "Migrar todo el historico documental" es weakly supported para alcance base; puede ser evolucion funcional futura si se confirma volumen, valor y riesgo. [SRC-001] [SRC-006]
- "Cerrar schema final, endpoints, CI/CD, nombres de skills/agentes o estructura interna VPS" no corresponde a Stage 01. [SRC-002]
- "Cerrar precio, SLA, contrato o anexos legales" no corresponde a Stage 01 y requiere informacion externa. [SRC-015]
- "Responder automaticamente consultas especificas de expediente sin fuente clara" debe considerarse fuera de autonomia por defecto hasta que Stage 03 defina limites y evals. [SRC-008] [SRC-010] [SRC-015]

## Handoff to Next Stage

Stage 02 debe convertir este audit en una decision de alcance base interno, sin escribir blueprint tecnico final. Debe priorizar problemas reales: radar BDNS/Canarias, atencion cliente/comercial, documentacion gobernada, adopcion no tecnica, CRM/memoria comercial, analisis repetitivo, campanas con aprobacion y seguridad/evals.

Stage 02 no debe tratar Hermes/Kapso/n8n como opciones abiertas de direccion arquitectonica: Hermes sera core agentic salvo bloqueo grave, Kapso + Hermes sera la via objetivo de WhatsApp salvo bloqueo grave, y n8n queda fuera del core. Lo que si debe decidir es cuanto de cada problema entra en el alcance base, que queda como evolucion funcional futura y que advertencias "do-not-sell-this-yet" aplican por Google Workspace, RGPD/opt-in, CRM, BDNS, Kapso/Meta y datos reales de atencion.
